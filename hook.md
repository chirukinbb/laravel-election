# Алгоритм выбора темы хука для Upwork

## Цель хука

Хук нужен не для продажи себя.

Хук нужен для того, чтобы клиент понял:

- исполнитель прочитал вакансию;
- исполнитель понял задачу;
- исполнитель уже начал думать над решением.

Хук должен быть коротким (1–2 предложения) и привязанным к конкретной вакансии.

---

# Шаг 1. Определить центральную тему вакансии

Перед написанием хука определить, вокруг чего построено описание.

Выбрать только одну основную тему.

## 1. Проблема / Боль

Использовать если клиент описывает:

- ошибки;
- нестабильность;
- recurring issues;
- баги;
- сложности;
- жалобы на текущую реализацию.

### Пример

> Recurring API issues обычно говорят не о единичном баге, а о необходимости пересмотреть подход к интеграциям.

---

## 2. Рост продукта

Использовать если клиент пишет:

- existing product;
- production app;
- growing platform;
- scaling;
- new features.

### Пример

> Когда продукт уже находится в продакшене, новые функции становятся проще задачей, чем сохранение чистой и поддерживаемой архитектуры.

---

## 3. Качество кода

Использовать если клиент акцентирует внимание на:

- clean code;
- maintainability;
- scalability;
- architecture;
- technical debt.

### Пример

> По описанию видно, что для вас важна поддерживаемость кодовой базы, а не просто быстрое закрытие задач.

---

## 4. Скорость разработки

Использовать если клиент говорит про:

- MVP;
- deadlines;
- fast delivery;
- quick launch.

### Пример

> Для MVP скорость получения работающей версии обычно важнее реализации полного набора функций.

---

## 5. Бизнес-цель

Использовать если клиент больше говорит о результате бизнеса, чем о технологиях.

### Пример

> Судя по описанию, задача заключается не просто в разработке функционала, а в дальнейшем развитии продукта без потери качества.

---

## 6. Архитектура

Использовать если задача связана с:

- интеграциями;
- SaaS;
- микросервисами;
- API;
- очередями;
- сложной логикой.

### Пример

> На существующих SaaS-проектах новые функции редко становятся проблемой сами по себе. Обычно сложность возникает при интеграции их в уже работающую систему.

---

## 7. Релевантный опыт

Использовать если у исполнителя есть опыт в той же нише, продукте или бизнес-домене, что и у клиента.

Например:

* carsharing;
* car rental;
* marketplace;
* SaaS;
* fintech;
* healthcare;
* logistics;
* real estate;
* booking systems;
* eCommerce;
* CRM/ERP.

Важно:

Релевантный опыт не должен превращаться в рассказ о себе.

Хук по-прежнему начинается с проекта клиента, а опыт используется как подтверждение понимания задачи.

### Плохо

> I have 8 years of Laravel experience.

> I worked on many SaaS projects.

### Хорошо

> Для carsharing-платформ основные сложности обычно возникают не в реализации новых функций, а в сохранении стабильности существующих процессов бронирования, оплаты и управления автопарком. С похожими сценариями мне уже приходилось работать ранее.

---

> На маркетплейсах рост функциональности почти всегда приводит к усложнению интеграций и бизнес-логики. С подобными системами я работал ранее, поэтому хорошо понимаю типичные точки риска.

---

> Для booking-платформ новые функции обычно затрагивают существующие процессы доступности, расписаний и оплат. С похожими продуктами мне уже приходилось работать на практике.

### Когда использовать

Использовать только если релевантный опыт действительно существует и напрямую связан с задачей клиента.

Если опыт отсутствует, лучше строить хук вокруг проблемы, архитектуры, роста продукта или бизнес-цели, чем пытаться
искусственно привязать себя к домену.

# Шаг 2. Если в вакансии есть вопрос

Если клиент задаёт вопрос:

- How would you approach...?
- How would you solve...?
- What would be your strategy...?
- How would you implement...?

То хук строится вокруг общего подхода к решению.

Важно:

- не расписывать решение подробно;
- не писать код;
- показать направление мысли.

## Формула

Проблема → подход → ожидаемый результат

### Пример

Вакансия:

> How would you approach a queue-heavy feature?

Хук:

> Для queue-heavy функционала я обычно начинаю с проектирования идемпотентных задач и безопасной обработки ошибок. Это позволяет сохранять предсказуемость системы даже при росте нагрузки.

---

Вакансия:

> How would you approach API synchronization?

Хук:

> Для синхронизации через API ключевым обычно является контроль консистентности данных и корректная обработка конфликтов между системами.

---

# Шаг 3. Если тема не очевидна

Использовать один из универсальных вариантов.

## Наблюдение

> Для проектов такого типа сложность обычно находится не там, где ожидают изначально.

---

## Масштаб

> Когда приложение уже находится в продакшене, требования к изменениям становятся существенно выше, чем на стадии MVP.

---

## Процесс

> Для долгосрочного сотрудничества обычно важнее качество решений и коммуникация, чем скорость реализации отдельных задач.

---

## Архитектура

> На существующих проектах новые функции редко становятся основной сложностью. Чаще всего задача заключается в том, чтобы встроить их в уже работающую систему без появления технического долга.

---

# Проверка качества хука

После написания задать себе вопросы:

1. Можно ли отправить этот хук в 10 других вакансий без изменений?
    - Если да — хук слишком общий, нужно переписать.

2. Есть ли связь между хуком и текстом вакансии?
    - Если нет — хук нужно переписать, чтобы укрепить связь с текстом вакансии.

3. Показывает ли хук понимание задачи или контекста?
    - Если нет — хук слабый, нужно укрепить понимание задачи или контекста.

4. Начинается ли хук с задачи клиента, а не с исполнителя?
    - Если нет — переписать, чтобы хук начался с задачи клиента, а не с исполнителя.

---

# Что запрещено

Не начинать отклик с:

- Hi, my name is...
- I am a senior developer...
- I have X years of experience...
- Thank you for posting this job...
- I can help you with this project...

Не использовать хук как пересказ ТЗ.

Не делать хук биографией исполнителя.

Не делать хук списком технологий.
